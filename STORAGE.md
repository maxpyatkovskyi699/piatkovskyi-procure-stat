# Storage & Performance Benchmarks (ProcureStat)

Цей документ містить архітектурний опис рівня персистентності бази даних SQLite та результати практичних експериментальних вимірювань продуктивності для платформи `procure_stat`.

---

## 1. Архітектура сховища та транзакції

Рівень зберігання побудований на базі SQLAlchemy ORM із використанням strict Pydantic v2 валідації на рівні доменної моделі. Для гарантії цілісності даних (ACID) та забезпечення максимальної швидкодії реалізовано такі принципи:

- **Управління транзакціями через `session_scope`:** Репозиторії не виконують `commit()` самостійно. Увесь життєвий цикл транзакції контролюється зовнішнім контекстним менеджером, що гарантує автоматичний відкат (`rollback`) у разі будь-яких збоїв.
- **Ідемпотентність:** Масові записи використовують метод `session.merge()`, що запобігає дублюванню рядків при повторному завантаженні однакових пакетів за унікальним ідентифікатором (`id` / UUIDv4).

---

## 2. Досліди та результати бенчмарків

Нижче наведено результати емпіричних тестів, виконаних за допомогою автоматизованих вимірювань (`pytest tests/test_storage_benchmarks.py`).

### Дослід 1. Вплив індексу та вибірковості полів

- **Умови:** База даних містить 5 000 записів із високою вибірковістю поля `company` (50 унікальних значень). Запит: пошук за конкретною компанією.

| Стан            | План виконання (`EXPLAIN QUERY PLAN`)                     | Час виконання |
| :-------------- | :-------------------------------------------------------- | :------------ |
| **БЕЗ індексу** | `SCAN procurements` (повне сканування таблиці)            | ~1.15 мс      |
| **З ІНДЕКСОМ**  | `SEARCH procurements USING INDEX idx_company (company=?)` | ~0.51 мс      |

> **Висновок:** Навіть на відносно невеликій вибірці індекс прискорює пошук за високоселективним полем. На великих промислових обсягах даних (десятки тисяч рядків і більше) наявність B-Tree індексу знижує час виконання запитів у десятки й сотні разів, уникаючи витратного Full Table Scan.

---

### Дослід 2. Вплив межі транзакцій (Transaction Boundaries)

- **Умови:** Масове збереження пакета з 1,000 записів у середовищі SQLite (файлова база). Порівнювався поштучний запис із комітом після кожного рядка проти пакетного запису з єдиним комітом наприкінці.

| Стратегія комітів                | Загальний час (1000 записів) | Пояснення / Причина                                                                                                                  |
| :------------------------------- | :--------------------------- | :----------------------------------------------------------------------------------------------------------------------------------- |
| **Коміт після кожного рядка**    | **4.864 сек**                | Кожен `COMMIT` змушує ОС та SQLite фізично скидати журнали транзакцій на диск (дисковий I/O), створюючи величезне «вузьке горлечко». |
| **Один коміт наприкінці пакета** | **0.290 сек**                | **У ~16.7 разів швидше!** Зміни кешуються в пам'яті, а на диск записуються єдиним швидким потоком у межах однієї транзакції.         |

> **Архітектурний висновок:** Отримані результати наочно пояснюють, чому репозиторій та сервісний шар проекту спроєктовані для роботи з пакетами (батчами) і використовують єдиний спільний `commit` наприкінці операції. Це забезпечує максимальну продуктивність без втрати надійності.
